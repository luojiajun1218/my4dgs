# 延后稀疏约束的三帧诊断

检查前 50 帧画质下降是否与稀疏约束过早有关。本轮只诊断帧 50–52，不是完整序列实验，也不能用于宣称达到 300 帧目标。

从 stableparent 实验已完成的第 49 帧 checkpoint 复制状态，所有张量保持相同，只修改副本中的配置元数据。将 rate warmup/ramp 从 20/20 改成 300/200：前 200 步只学区域，201–300 步允许 GS 自由拟合，301–500 步逐渐增加稀疏约束，最后 100 步使用原有完整权重 0.015。其他训练参数不变。三帧分支从独立的 `reference_frame49.npz` 解码。

| 帧 | 原配置 PSNR | 延后约束 PSNR | 原配置字节 | 延后约束字节 |
|---|---:|---:|---:|---:|
| 50 | 32.92881 | 33.47663 | 33,651 | 809,688 |
| 51 | 33.12463 | 33.82303 | 34,110 | 930,516 |
| 52 | 33.00696 | 33.79644 | 35,399 | 772,993 |

平均画质提高约 0.679 dB，但平均增量达到 837,732 字节，远超 50 KB。每帧约 10.5–12.9 万个旧 GS 保留局部残差。自由拟合阶段能找回运动细节，但现有后段稀疏强度不足以再消掉这些已经形成的残差；仅延后约束不能达到目标。本轮没有测 FPS，也没有将这三个分支帧混入完整实验。

首次启动诊断暴露了恢复问题：`torch.load(map_location='cuda')` 将解码状态中的 CPU 张量一起迁移到 GPU，随后计算树编辑元数据时发生设备不一致。修正 `DecodedState.restore`，恢复为 CPU 连续张量并保留 dtype。两项恢复检查及真实 frame49→frame50 损失/导出冒烟通过后，使用 v2 独立目录重跑。原始完整实验运行代码不变，短诊断结束后恢复原进程。
