# 增量播放的并行解析与 nearest-leaf 协作路由

本次完成实现、单元检查和已有 v24 全300帧的一致性核验。没有重新训练，尚未取得此版本的独占播放 FPS。

## 已观测的瓶颈

上一版播放器 e2dfa41 在 v24 完整299次动态更新、三轮独占计时中为82.470372 FPS，包含读包、解码、属性预测、上传、GPU更新与实际渲染。主线程推进约7.4..7.9ms/帧；只读诊断预先解析30个真实包时，推进调用约3.3ms/帧。这提示并发解析可能产生调度或GIL竞争，不能由两个不同运行的差值精确归因。

原CUDA路径对于支持球之外的每个点，由一个线程遍历4050个叶代表，寻找最近叶。保持相同路由规则可以改变并行方式，无需更换表示或量化。

## 实现改动

- 稀疏解析从两个线程改为两个spawn进程，各自使用一个Torch CPU线程；最多预取两个未来稀疏包，不缓存未来稠密状态或图像。
- 球外点压入设备工作队列，每个点由一个256线程block协作遍历叶代表。距离仍按原float64运算顺序计算，相等时选择最早叶索引；球内点保持原空间路由。
- 两个CUDA入口在调用期间释放Python GIL。固定设备工作队列复用，不下载球外点计数来驱动kernel。
- 独立核验和正式播放都使用实际进程传输路径。一次性的worker启动计入启动成本，实际文件读取、解压、校验和及进程传输仍在播放计时内。

文件为`stream_update/update.cpp`、`update.cu`、`gpu_stream.py`和`benchmark_gpu_stream.py`。没有改变训练方法、包字节、属性精度、预测器或渲染器。
